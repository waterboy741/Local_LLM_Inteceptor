# Project completion plan

Status: planning checkpoint, October 22, 2026. M0–M5 are complete under their offline criteria. The application currently works as an **explicit HTTP proxy**: a local or remote client must point its Ollama base URL at the displayed listener. A request from a second device through that path was manually verified earlier. Transparent interception with an unchanged server URL is **not implemented or verified**. M6 is still open.

The committed M6 groundwork includes immutable session/PF/ARP plans, an offline session and rollback model, bounded Unix-socket Heartbeat/Stop transport, read-only interface/route/neighbor/PF diagnostics, and an offline scoped PF anchor operation adapter. A further bounded PF process runner is **unfinished, unreviewed, and uncommitted** in the working tree at this checkpoint. Keep it separate from the completed adapter until it passes review and all required checks. The client and Ollama devices are off today; all remaining lab actions below wait until they are available.

## 2. Transparent HTTP passing and ARP redirection

The intended transparent flow is: OpenCode sends HTTP to the original Ollama IP/port; the client's Ethernet destination becomes the research Mac after a scoped ARP change; the Mac receives a frame addressed to its MAC but carrying the server's destination IP; a verified PF translation sends that one TCP flow to the local proxy; the proxy opens a separate connection to the configured Ollama IP/port; response traffic returns to the client with the original server identity preserved. Other traffic between the devices must continue normally. Each link of that flow needs its own proof; receiving a frame at the Mac does not by itself make the IP stack deliver it to a local socket.

### Offline implementation sequence

1. **Finish the PF command runner checkpoint.** Complete independent review of the paused, uncommitted runner; resolve process-start, timeout, bounded-output, kill/reap, and partial-failure cases. Run its fake-child tests and the debug/release/sanitizer suites. Commit and push it only after the repository's implementation, test, and review votes are all COMPLETE. The runner must remain unwired until the authorization and rollback backend exists.
2. **Build the narrowly scoped privileged backend.** Implement a host-wide exclusive session lease, effective-privilege check, fresh selected-interface/proxy readiness checks, PF-reference ownership, exact anchor ownership/attachment verification, and a durable recovery journal. A failed or timed-out rule operation may have applied; record cleanup ownership before trying it. Never replace or flush the global ruleset or unrelated state. The current offline `SystemOperations` contract for atomic compare-and-set settings needs a real safe mechanism or a documented redesign before enabling forwarding changes.
3. **Prove PF interception with synthetic HTTP before ARP.** On the research Mac, use an isolated, explicitly activated test path to check the generated rule syntax, active filter and translation attachment points, rule order, `set skip` interactions, a fresh SYN reaching the intended listener, and packet/state/counter evidence. Verify how macOS handles the planned inbound `rdr` to loopback and reverse translation; revise the rule design if the tested OS does not deliver or translate as assumed. Keep the listener's upstream connection outside the inbound redirection match to prevent recursion.
4. **Implement receive/forward handling for diverted frames.** Once the Mac receives traffic addressed to its MAC but not its IP, the selected interface, PF/routing path, and IP forwarding must deliver only the target HTTP flow to the proxy while preserving the original client/server connection semantics. Traffic not selected for interception needs a safe bypass in both directions. Validate checksums, MTU, existing TCP state, and per-interface behavior with synthetic captures; do not rely on promiscuous capture as a forwarding mechanism.
5. **Implement controlled ARP direction and restoration.** Use the validated immutable session snapshot to identify client/server MACs, send only targeted neighbor updates for the authorized pair on the selected interface, and refresh only while the session is healthy. The client must associate the Ollama IP with the research Mac's MAC; if bidirectional bypass/forwarding needs the server's view of the client changed too, verify and apply that separately. Test whether this Wi-Fi/AP and each OS accept the updates. On Stop, timeout, interface loss, or failure, stop refresh and send corrective updates from the recorded genuine peer MACs; then verify resolution and traffic recovery. Never treat a sent ARP frame as proof that a peer changed its cache.
6. **Wire lifecycle with fail-closed recovery.** Add authenticated Start/Stop/Heartbeat bootstrap to the installed helper; run a watchdog independently of the GUI; bind activation to a frozen client/server/interface/port snapshot. Verify installation, restart, lease collision, stale owner, GUI crash, helper crash, proxy crash, and partial startup. Cleanup must retain ownership and show `CleanupPending` when restoration cannot be proven. The GUI must show active, stopping, and recovery states without implying success from a command exit alone.

### Lab proof gates, in order

1. Re-establish direct client↔server and Mac↔server reachability, current neighbor resolution, and the selected interface path. If these fail, repair the lab baseline before testing interception.
2. With ARP still off, verify the dedicated PF anchor is actually attached and evaluated using fresh synthetic TCP traffic and scoped counters/state. Confirm the local proxy gets exactly one request and the server gets exactly one upstream request.
3. Activate ARP for only the authorized client/server pair. Observe the client's neighbor entry, destination MAC at the research Mac, corresponding inbound packet, translated connection, upstream connection, and client-visible reply. Verify that the client still uses the server's original IP/port and does not require an OpenCode setting change.
4. Exercise a nonmatching HTTP path, non-LLM TCP traffic, and both traffic directions. Verify bypass without loops, black holes, or changes to unrelated devices. Then test default and nondefault server ports, streaming responses, and short/long modified JSON bodies against the mock server before using Ollama.
5. Repeat Start/Stop and deliberate failure tests. Measure restoration of peer neighbor entries, PF rules/state/reference ownership, forwarding settings, existing connection behavior, and time to ordinary connectivity. Record any Wi-Fi/AP limitation explicitly; a blocked ARP path means transparent mode is unsupported on that topology.

The acceptance result is a repeatable, opt-in, unchanged-client-URL walkthrough with sanitized evidence for each gate, plus successful cleanup and no unrelated network changes. Offline rule generation, read-only diagnostics, or the previously verified explicit proxy cannot substitute for these observations.

## 3. Remaining work to finish the application

1. **Product integration and clear modes.** Add a deliberate Transparent mode only after the helper and live gates work. Keep Local explicit proxy and Remote explicit proxy usable. Show configured server endpoint, selected interface/client, listener, active mode, readiness checks, and actionable failures. Prevent changing a live session's routing inputs and prevent conflicting sessions. Make Stop and recovery controls visible even if the GUI reconnects to a surviving helper.
2. **HTTP correctness and modification behavior.** Re-run Observe, Hold, and automatic modifiers through the transparent path. Verify original request bodies in Observe, exact edited bodies in Modify, content-length/chunked handling, first-request model warm-up, timeouts, client disconnects, and native streaming. `/v1/chat/completions` remains the default path alongside native Ollama paths; the configured server IP and port must remain user-editable. Retained request display, `messages`/last-message views, JSON formatting, audit, export/import, and offline replay must still work without changing forwarded bytes unintentionally.
3. **Security and data handling.** Enforce client/server/interface/port scope, helper authentication and least privilege, bounded IPC and child processes, ownership checks, no shell commands, no global PF mutation, and a single active lease. Keep prompts, credentials, raw captures, machine addresses, and recovery tokens out of committed artifacts and default diagnostics. Add a recovery procedure that reports uncertainty rather than claiming cleanup when a process, PF operation, or neighbor update cannot be verified.
4. **Deterministic and live validation.** Maintain fake-backed tests for parsing, malformed/truncated ARP, invalid commands, partial writes, timeouts, output bounds, lost heartbeats, crash/restart recovery, rule collisions, concurrent state changes, and repeated cleanup. Keep live tests opt-in and separate from ordinary CTest. Run debug, release, sanitizer, and GitHub Actions on each reviewed increment; inspect CI after pushes. Use sanitized synthetic lab evidence and record performance against agreed latency, time-to-first-byte, throughput, memory, and recovery targets before declaring M6 complete.
5. **Packaging and operations.** Produce a reproducible macOS package with the helper and its installation/uninstallation path, privilege prompts, version compatibility, logs/status, and a rollback/uninstall guide. The current unsigned app package does not grant PF/ARP privileges. Validate fresh installation, upgrade, stop, uninstall, and post-crash recovery on the target Mac. Update README/runbooks with exact steps, limitations, and a supported macOS/version matrix established by testing.
6. **Milestone closeout.** Resolve review findings, obtain separate production/test/review COMPLETE votes as required by `AGENTS.md`, run the relevant full suites, check the working tree and diff, commit focused increments, push the tracked branch, and verify remote SHA and CI. Mark M6 complete only after the transparent lab gates and helper/recovery/package walkthrough pass. If a topology or OS limitation prevents them, document the supported explicit-proxy scope and leave transparent M6 acceptance open rather than reporting a partial result as complete.
